01 Overview

"Fleurs by Liza" is a live flower e‑commerce site serving Algeria. It is guest‑checkout only — there is no customer login/account system, by explicit design. The storefront is 5 static HTML files with no build step, backed entirely by Supabase (Postgres + RLS + Storage + Edge Functions).

Standing constraints — do not violate
  • No customer accounts/login. Guest checkout only.
  • No Stock/Inventory. Built once, fully and deliberately removed. Do not reintroduce under any name.
  • Occasions: owner's recent instructions say "do not add" — but it already shipped earlier in the project's history and exists live today. See §11 before touching it.
  • Never weaken RLS/auth/security. Never expose secrets in frontend code, logs, or commits.
  • Never claim a feature works without testing it against the real Supabase project.
  • Clean up all test data after testing; never touch real customer/order/business data without confirming it's test data first.
  • Preserve existing working design/features — no reverts. Never fake payments, emails, or integrations.
  • The assistant on this project has a self‑imposed rule to never log in as admin — so anything gated behind a real admin JWT cannot be live‑tested from a session; see §8.
  • Per feature: implement → test on real Supabase → fix → regression test → commit → push → verify local HEAD == origin/main.

Post‑order status — receipt upload, invoice, delivery proof, reviews, order status.

Full admin dashboard, ~3000+ lines, email/password login gate.

Backend: Supabase project lgpllhbabctsdplqapzi — Postgres with RLS on every table, one Edge Function (hyper-action, Deno), pg_cron for scheduled trash purge, and 3 storage buckets. Repo: local git at C:\Users\maamr\Downloads, migration/function source under flz_audit\.

Trust model — important to preserve

The frontend is fully untrusted. All pricing (product price, delivery cost, coupon discount, deposit amount) is recomputed server‑side from authoritative DB state by the orders_secure_insert trigger on every insert into orders. The client only ever sends product IDs, quantities, wilaya/commune, and a coupon code — never a price the server trusts. RLS denies anon direct access to orders; all order operations go through SECURITY DEFINER RPCs that re‑validate everything internally.

06 RLS & security decisions

Do not weaken any of these.

  • orders — anon has no direct SELECT/UPDATE. All reads via get_order_by_token (exact token required — the original bug only checked receipt_token IS NOT NULL, letting anyone list every order). All writes via SECURITY DEFINER RPCs.
  • orders_guard_anon_update — independent defense‑in‑depth: resets protected fields, blocks re‑marking a paid order, restricts which payment_status values a non‑privileged caller can ever set.
  • receipts / delivery_proofs buckets — private, admin‑only listing; customers get only a short‑lived signed URL scoped to their own order.
  • settings — anon read‑only, via two separate whitelists (RPC + RLS policy) that must be kept in sync manually. No anon write.
  • delivery_prices — anon read (for the dropdowns), no write. Confirmed this session.
  • Admin‑gated Edge Function actions — verify a real Supabase Auth JWT against /auth/v1/user, then check profiles.role='admin'.
  • idFilter() — strict regex allow‑list for order lookups, preventing injection‑adjacent abuse of dynamic filters.
  • SlickPay webhook — no JWT, but every call is re‑verified against SlickPay's own API before an order is ever marked paid.

12 Delivery pricing — wilaya + commune critical bug fixed this session

Design (already correct, pre‑existing)

delivery_prices has one row per wilaya (home_price, office_price, active) plus a communes JSONB array. resolve_delivery(wilaya_id, commune) is the single authority: a commune with a non‑null home_price override wins; otherwise it falls back to the wilaya's flat rate. Called from orders_secure_insert for both single‑item and cart orders — one code path.

The critical bug, found and fixed this session

Real production data for 57 of 58 wilayas stored communes as a plain array of strings (["أدرار","رقان",...]) instead of the objects resolve_delivery() requires. Effect: calling it with any real commune raised "invalid commune for this wilaya" — checkout failed for any customer who selected a commune, nationwide, for 57 of 58 wilayas. (Only Algiers already had real object‑shaped per‑commune data.)

Fix — migration_28_normalize_communes.sql

  1. Every plain‑string commune converted to {"name": …, "home_price": null, "active": true}. home_price is deliberately null, not 0 — this falls back correctly to the wilaya's existing rate, i.e. exactly today's real pricing. No name, wilaya price, or existing override (Algiers') was changed.
  2. resolve_delivery() hardened to also tolerate a plain‑string commune directly, as defense‑in‑depth against this recurring from a future bulk import.

Client‑side companion bug, also fixed (checkout.html)

The commune <select> had no onchange handler at all — even a real price override never updated the on‑screen total before submit (the server always charged correctly regardless, but the preview didn't match). Added a getDeliveryCost() helper mirroring resolve_delivery()'s exact logic, wired into both single‑item and cart summaries. Disabled communes are now also filtered out of the dropdown.

Verified end‑to‑end

A real order submitted through the actual checkout UI — Algiers, commune "الحراش" (a real free‑delivery override, price 0) — succeeded (previously would have failed) with total = 50000, matching the preview exactly. Test order deleted after. Admin CRUD re‑tested live against the normalized data (temporarily set then reverted a real commune price), correctly scoped to one commune without touching others.

Yalidine tie‑in: shipment creation now looks up the correct Yalidine commune ID by matching against Yalidine's own list — see §8.
